# 念念知识卡生产流水线

## 目标

将零散资料转成可追溯、可验证、可分发的知识卡，并保持 `metadata/index.json`、详情 Markdown、可视化门户和 GitHub 历史一致。

知识卡是最小资产单位；详情 Markdown 是完整说明；`metadata/index.json` 是唯一门户索引。

## 触发场景

处理以下请求时启用本 Skill：

- “把这个腾讯文档、飞书、B站、GitHub 或网页资料入库”
- “把这个项目整理成知识卡”
- “把这段经验变成 SOP、方法卡或复盘卡”
- “提炼这个开源项目 / 视频的信息差”
- “更新知识库卡片、资料索引或工作流”

不用于直接发布公开内容、绕过来源权限、把未验证信息包装为可执行能力，或包含密钥、Cookie、用户媒体、签名 URL、账号信息的资料。

## 权威来源与范围

1. 先读取仓库根目录 `metadata/card-schema.md`，以其字段和状态约束为准。
2. 再读取 `E:/codex/niannianai/niannianai/authority/COMPOUNDING_KNOWLEDGE_AUTHORITY.md`，以其知识卡、三层分发和外部资料原则为准。
3. 只在当前知识库仓库中新增或修改知识资产；不得修改来源项目的业务代码。
4. 任何外部资料默认 `review`，任何本地未实测的方案默认 `draft`。
5. 只有已经证明可执行的资产才可标记 `verified`；只有经过推荐判断且近期有效的资产才可标记 `recommended`。

## 工作流

### 第 1 步：识别来源与边界

识别来源类型并保留原始信息：

| 来源 | `source.type` | 最低要求 |
|---|---|---|
| 腾讯文档 | `tencent-docs` | 原始链接、访问层级、文档标题 |
| 飞书 | `feishu` | 原始链接、访问层级、文档标题 |
| GitHub | `github` | 仓库链接、许可证、活跃度、适用边界 |
| B站 | `bilibili` | 视频链接、作者、发布时间、关键时间点 |
| 网站 | `website` | 原始链接、页面标题、抓取日期 |
| 本地项目 | `internal` | 真实路径、相关文件、验证证据 |

发现凭据、Cookie、账号、私密媒体或签名 URL 时，停止写入这些内容，只记录经脱敏后的能力描述和安全边界。

### 第 2 步：做“判断”而非只做摘要

从资料中提炼：

1. 用户到底能得到什么结果。
2. 解决哪个高频或高价值问题。
3. 是否可复用、可验证、可商业化。
4. 适合 `public`、`team`、`private` 中的哪些人群。
5. 是否需要前置账号、授权、部署、成本或人工操作。
6. 是否可安全提供“复制 / 下载 / 运行”等一键动作。

使用 1～5 分估算 `score`，综合需求强度、可复制性、结果确定性、商业潜力与更新稳定性。无法判断时给 1～2 分，不夸大价值。

### 第 3 步：选择卡片类型

- `tool`：独立工具、软件、网站或 API。
- `workflow`：从输入到交付的步骤化任务。
- `project`：念念系列或可复用项目案例。
- `automation`：FastAPI、Playwright、脚本、部署、任务回收等自动化链路。
- `method`：判断框架、SOP、选型方法。
- `retrospective`：成功或失败后的复盘。
- `insight`：有时效的信息差、趋势或高价值发现。

优先使用一张卡只讲清一件事；复杂资料可拆分为“项目卡 + 工作流卡 + 方法卡”。

### 第 4 步：生成知识卡草稿

1. 从 `docs/templates/knowledge-card.md` 复制结构到对应分类目录。
2. 填写详情页：一句话结论、问题、适合谁、输入→处理→输出、步骤、验收、失败边界、关联卡。
3. 在 `metadata/index.json` 新增唯一条目。
4. 外部资料保留 `source.type` 与 `source.url`；本地项目填写 `internal`，并在详情页写真实路径。
5. 初始动作至少提供 `detail`；未验证时不得虚构 `run`、`download`、`copy` 或外部打开动作。
6. 若事实不足，在详情页明确写“待确认 / 待验证”，不要补写推测。

### 第 5 步：校验与预览

执行：

```bash
npm --prefix "<knowledge-repo>" run validate
```

然后以本地 HTTP 服务打开 `dashboard/`，确认：

- 新卡能被加载。
- 标题、摘要、标签、分发层、状态和评分正确。
- 详情入口可打开。
- 没有把私有或未验证资产误标为公开、推荐或一键可用。

校验失败时先修正索引或缺失文件，不能跳过。

### 第 6 步：提交前审查

默认停在“本地草稿 + 校验通过”，向用户展示：

- 新增 / 修改了哪些卡。
- 来源、状态、分发层和评分。
- 是否存在待验证项。
- 将要提交的 Git 变更。

只有用户明确要求提交时，创建独立、可审查的 Git 提交。只有用户明确要求推送或发布时，才推送 GitHub、创建 PR 或改变仓库可见性。

## 分发决策

- `public`：适合展示、可安全传播的结论、公开工具或入门流程；不得暴露内部实现、账号或核心商业资产。
- `team`：可包含 SOP、部署与验收细节；仍不得提交密钥和用户数据。
- `private`：可包含高级交付、模板和受控资产；必须保留实际权限控制，不能仅依赖元数据。

同一知识优先维护一份来源明确的主卡，再按分发层控制展示深度，不维护三份互相漂移的副本。

## 常用示例

- “把这个 B站视频入库”：记录视频 URL、作者、时间点；生成 `insight` 或 `workflow` 草稿；状态为 `review`。
- “把这个 GitHub 项目做成卡”：生成 `tool` 或 `project` 草稿；写清许可证、适用问题、部署门槛与风险；状态为 `review`。
- “把念念 AI 的视频服务沉淀下来”：生成 `automation` 卡；引用真实路径与验证证据；可在已有实测基础上标为 `verified`。
- “把一次排错经验做成团队 SOP”：生成 `retrospective` 或 `method` 卡；写清触发条件、根因、步骤、验证和不适用范围。

## 完成标准

仅当以下条件全部满足时，才称为“已入库”：

- Markdown 详情存在。
- `metadata/index.json` 条目完整且唯一。
- `npm run validate` 通过。
- 来源、状态、分发层和维护人已标注。
- 未验证或敏感内容没有被误标或泄露。
- 已按用户授权决定是否提交、推送或发布。
